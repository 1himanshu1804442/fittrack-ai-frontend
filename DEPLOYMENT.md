# 🚀 Deployment Guide & Troubleshooting Log

This document records the complete cloud deployment process for FitTrack AI, including every real-world error encountered and how each was diagnosed and resolved.

---

## Architecture Overview

```
┌──────────────┐       ┌──────────────┐       ┌──────────────┐
│   Frontend   │──────▶│   Backend    │──────▶│   Database   │
│   (Vercel)   │ proxy │  (Railway)   │ JDBC  │   (Neon)     │
│  React/Vite  │──────▶│ Spring Boot  │──────▶│ PostgreSQL   │
└──────────────┘       └──────────────┘       └──────────────┘
```

| Layer      | Platform | Tech Stack                  |
|:-----------|:---------|:----------------------------|
| Frontend   | Vercel   | React 19, Vite, TailwindCSS |
| Backend    | Railway  | Spring Boot 4.0.6, Java 17  |
| Database   | Neon     | PostgreSQL (Serverless)     |

## Deployment Steps

### 1. Database (Neon)
- Created a free serverless PostgreSQL instance on [neon.tech](https://neon.tech)
- Region: `ap-southeast-1` (Singapore)
- Obtained the connection string in the format:
  ```
  postgresql://<user>:<password>@<host>/<dbname>?sslmode=require
  ```

### 2. Backend (Railway)
- Connected the GitHub repository (`fittrack-ai-backend`) to [Railway](https://railway.app)
- Railway auto-detected the `pom.xml` and built the Java Maven project
- Added the following environment variables:

| Variable                    | Purpose                              |
|:----------------------------|:-------------------------------------|
| `SPRING_DATASOURCE_URL`     | JDBC connection to Neon PostgreSQL   |
| `SPRING_DATASOURCE_USERNAME`| Database username                    |
| `SPRING_DATASOURCE_PASSWORD`| Database password                    |
| `GEMINI_API_KEY`            | Google Gemini AI API key             |
| `JWT_SECRET`                | Secret key for JWT token signing     |
| `PORT`                      | Application port (8080)              |

- Generated a public domain via Railway Settings → Networking → Generate Domain

### 3. Frontend (Vercel)
- Connected the GitHub repository (`fittrack-ai-frontend`) to [Vercel](https://vercel.com)
- Added `VITE_API_BASE` environment variable pointing to the Railway backend URL
- Configured `vercel.json` for API proxy rewrites (see Error #4 below)

## 🐛 Errors Encountered & Resolutions

### Error #1: Spring Boot Startup Crash — Missing Environment Variables

**Symptom:**
```
Could not resolve placeholder 'jwt.secret' in value "${jwt.secret}"
```

**Root Cause:**
Spring Boot 4.x uses strict placeholder resolution. The `application.properties` file referenced `${JWT_SECRET}` but no default value was provided. When running locally without the env var set, the application crashed on startup.

**Fix:**
Added a fallback default value in `application.properties`:
```properties
jwt.secret=${JWT_SECRET:default_jwt_secret_for_local_dev_only_change_in_production}
```

**Lesson Learned:**
Always provide sensible defaults for environment variables in Spring Boot properties files to prevent startup crashes in development environments.

---

### Error #2: DemoApplicationTests Failing — Context Load Error

**Symptom:**
```
DemoApplicationTests.contextLoads » IllegalState Failed to load ApplicationContext
```

**Root Cause:**
The default `DemoApplicationTests.java` generated by Spring Initializr uses `@SpringBootTest`, which attempts to load the full application context including database connections. In a CI/test environment without a live database, this test always fails.

**Fix:**
Removed the auto-generated integration test and replaced it with focused unit tests (`UserServiceTest`, `RecommendationServiceTest`) that use Mockito to mock all external dependencies.

**Lesson Learned:**
Auto-generated integration tests should be replaced with proper unit tests that mock external services. This follows the **Test Pyramid** principle — many fast unit tests, few slow integration tests.

### Error #3: Vercel Environment Variables Not Applied — The Localhost Trap

**Symptom:**
- App worked perfectly on the development laptop via the Vercel URL
- App completely failed on mobile phones with "Registration failed"
- Misleading error message: "Username might be taken"

**Root Cause:**
Vite bakes environment variables into the JavaScript bundle **at build time**, not at runtime. Adding `VITE_API_BASE` in Vercel's dashboard after the initial deployment did NOT automatically update the already-built bundle. The frontend was still calling `http://localhost:8080`.

Why it appeared to work on the laptop: the developer's local Spring Boot server was still running on `localhost:8080`, so the browser accidentally connected to it. On a phone, `localhost` points to the phone itself (which has no server), causing an instant failure.

**Diagnosis:**
Updated the `catch` block in `Register.jsx` to display the actual error:
```javascript
// Before (hiding real errors):
catch {
    toast.error("Registration failed. Username might be taken.")
}

// After (showing real errors):
catch (err) {
    toast.error(`Error: ${err.message}`, { duration: 8000 })
}
```

This revealed the true error was `Failed to fetch` — a network-level failure, not a username conflict.

**Fix (Attempted):**
1. Added `VITE_API_BASE` in Vercel dashboard
2. Redeployed with "Use existing Build Cache" unchecked
3. Hardcoded the Railway URL directly in the source code

**Lesson Learned:**
- Vite env vars are compile-time, not runtime. Always redeploy after adding them.
- Never use generic error messages in catch blocks during development. Always surface the real error.
- Always test deployed apps on a device that does NOT have the local dev server running.

### Error #4: Mobile Carrier Blocking — "Failed to fetch" on Phone Only

**Symptom:**
```
Error: Failed to fetch
```
- App worked on laptop (any browser) via the Vercel URL
- App failed on every mobile browser with "Failed to fetch"
- Local backend was NOT running, confirming the laptop was hitting Railway correctly

**Root Cause:**
Indian mobile carriers (Vi/Vodafone, Jio, Airtel) sometimes block or fail to resolve DNS for certain cloud hosting domains like `*.up.railway.app`. The phone's browser could not establish a TCP connection to the Railway backend at all.

**Diagnosis:**
1. Confirmed the Railway backend was healthy by hitting it from the laptop: `curl.exe -I https://fittrack-ai-backend-production.up.railway.app/v3/api-docs` returned `HTTP/1.1 200 OK`
2. The phone could load the Vercel frontend (proving the phone had internet)
3. The phone could NOT reach the Railway backend directly (proving it was a carrier-level block)

**Fix:**
Configured **Vercel Rewrites** to proxy all API requests through Vercel's own domain, bypassing the mobile carrier block entirely.

Created `vercel.json`:
```json
{
  "rewrites": [
    {
      "source": "/api/:path*",
      "destination": "https://fittrack-ai-backend-production.up.railway.app/api/:path*"
    }
  ]
}
```

Changed `API_BASE` from the Railway URL to an empty string `''`, so all `/api/*` requests go to the Vercel domain first, and Vercel silently forwards them to Railway.

**Before:**
```
Phone → railway.app ❌ (blocked by carrier)
```

**After:**
```
Phone → vercel.app/api/* → Vercel proxies to railway.app ✅
```

**Lesson Learned:**
- When deploying for users in India, always consider that mobile carriers may block niche cloud domains.
- Using your frontend hosting provider (Vercel/Netlify) as a reverse proxy is a clean, production-grade solution that also eliminates CORS issues entirely.
- This is the same pattern used by companies like Netflix, Stripe, and Vercel themselves in production.

### Error #5: White Bar at Top of Page — CSS Default Override

**Symptom:**
A thin white horizontal bar appeared at the very top of the page above the dark-themed dashboard.

**Root Cause:**
Browsers apply a default `background-color: white` to the `<body>` element. The React app's dark background (`#080C10`) was applied to the root component `<div>`, but the underlying `<body>` tag still had a white background. Any sub-pixel gap caused by margin, padding, or zoom revealed this white layer.

**Fix:**
Added global styles in `index.css`:
```css
html, body, #root {
  margin: 0;
  padding: 0;
  height: 100%;
  background-color: #080C10;
}
```

**Lesson Learned:**
Always reset the `html` and `body` background color to match your app's theme. Browser defaults are designed for white-background documents, not modern dark-themed SPAs.

## Key Takeaways

1. **Always show real errors during development** — Generic messages like "Something went wrong" make debugging 10x harder.
2. **Test on real devices** — Bugs that are invisible on localhost appear instantly on a phone over mobile data.
3. **Environment variables in Vite are build-time** — They must be set BEFORE the build, not after.
4. **Use reverse proxies** — Routing API calls through your frontend domain (Vercel rewrites) eliminates both CORS and carrier-blocking issues.
5. **Provide env var defaults** — Spring Boot apps should always have fallback values to prevent crashes in different environments.
